# 品牌知识更新与监测问题处理流程设计

## 目标

从可见性监测的品牌知识维护入口，按截图实现“确认品牌知识修改 → 全部已启用市场暂停并生成推荐题 → 分市场选择推荐题 → 统一开启市场”的完整前端交互。后端是市场状态、处理进度、推荐题和修改次数的唯一事实来源；当前仓库没有这些业务 API，本期用类型化 mock 服务驱动界面，为后续真实接口替换保留边界。

## 用户确认的交互流程

1. 用户从可见性监测品牌知识区点击“维护品牌知识”，打开现有知识编辑弹窗。
2. 点击保存后，显示确认修改弹窗，概述此次影响的已启用市场、确认后统一暂停、修改次数及剩余次数。影响摘要和次数来自服务响应，不由组件自行推算。
3. 用户返回编辑时继续保留未提交内容。用户确认后，服务完成知识更新、暂停全部已启用市场并按市场生成 AI 推荐问题；成功后打开“各市场监测问题”界面。
4. 市场列表展示每个市场的暂停状态、待处理推荐题数和处理入口。用户进入一个市场后，可勾选至多 5 条推荐题并确认；未选择的推荐题不加入，已有监测问题继续保留。
5. 确认单市场选择后，返回市场列表并展示服务端更新后的状态。可继续处理其他市场；未处理市场保留原有监测问题。列表提供“开启全部市场”入口，成功后按服务端返回状态刷新。
6. 刷新或重新进入流程时，服务重新读取流程状态和进度；前端不将暂停、生成、已选或已处理状态写入 localStorage。

## 交互与状态

### 确认修改

- 保存编辑内容先展示确认，不在用户尚未确认时修改知识、暂停市场或生成推荐题。
- 确认信息展示后端提供的影响摘要、将扣除的修改次数和确认后的剩余次数。
- 确认提交期间禁用重复提交并显示处理中状态；成功后进入市场处理列表。
- 接口失败时留在当前步骤，保留编辑内容并允许重试；不显示成功或进入后续步骤。

### 市场列表与单市场选择

- 市场集合、暂停状态、待处理数量、推荐题候选及当前监测问题均由服务数据提供。
- 单市场候选区明确显示已选数量与上限 5；保存时只提交选中的候选 ID，不自动加入未选项。
- 保存成功后重新读取或使用接口返回的最新状态更新列表；失败时保留选择。
- “开启全部市场”按截图作为列表操作，不额外增加新的确认层。开启结果以服务返回为准。
- 空列表、无候选、读取中、提交中和服务错误都有明确反馈；错误可重试，不能静默吞掉。

## 服务边界与数据契约

新增面向该流程的类型化 service 模块。UI 不依赖 mock 实现细节；后续仅替换 service provider 为真实 API。服务操作至少包括：

- 读取品牌知识更新流程、各市场状态、候选推荐题和现有问题；
- 保存知识并预览/返回影响范围与修改次数；
- 确认修改，执行市场暂停与推荐题生成；
- 保存指定市场的推荐题选择；
- 开启全部市场。

流程数据需表达流程阶段、市场 ID/名称/语言、监测启用状态、待处理/已处理情况、候选问题、已选 ID、现有问题及服务端修改次数。确认操作应由服务端一次性校验并执行，避免知识已更新但暂停或生成失败时前端误报完整成功。若后端采用不同端点或阶段模型，适配层负责映射为 UI 使用的领域类型。

本期 mock 服务提供确定性的演示响应和可测试的状态变更，不写浏览器持久化；刷新后以 mock 初始数据重新读取。mock 数据显式标注为演示数据，不声称是真实市场状态或真实额度。

## 组件职责

```text
VisibilityMonitoringView
  └─ BrandKnowledgeUpdateFlow (流程容器：步骤、service 调用、加载/错误态)
       ├─ KnowledgeEditorDialog (复用：编辑品牌知识)
       ├─ BrandKnowledgeChangeConfirm (影响范围和修改次数确认)
       ├─ MarketRecommendationList (市场状态、待处理数量、进入处理、统一开启)
       └─ MarketRecommendationEditor (单市场候选选择与现有问题；最多选择 5 条)
```

- `VisibilityMonitoringView` 只负责入口和挂载流程容器，不持有市场处理业务状态。
- 流程容器协调编辑、确认、市场列表与单市场编辑步骤；调用 service 并提供统一的 pending/error 状态。
- 子组件通过明确的 props/events 通信；不直接调用 localStorage 或修改 Pinia 市场配置。
- 复用现有知识编辑组件，新增的弹窗和市场面板放在可见性监测 feature 目录，使用项目现有 UI 组件和样式 tokens。

## 视觉质量（最高优先级）

- 本流程的视觉完成度是首要验收标准，与流程正确性同为发布门槛；不能以“功能可用”代替视觉打磨。
- 以现有 GEO 工作台为视觉基线，并结合用户截图呈现层级；避免机械放大截图尺寸。整体应精致、克制、紧凑、易扫读，特别避免用户此前指出的弹窗过宽/过高、标题与按钮过大、留白失衡等问题。
- 弹窗按内容决定尺寸并适配视口；标题栏、正文、操作区比例协调，不留大片无意义空白，不因嵌套确认层造成视觉压迫。主次操作、关闭和返回路径清晰。
- 使用一致的字号层级、4/8px 间距节奏、控件高度、圆角、边框和阴影；优先使用项目语义 tokens。不要为单个弹窗随意引入新颜色、夸张阴影、重复卡片边框或不同风格图标。
- 市场列表需能快速比较状态与待处理数，市场信息和操作按钮对齐；推荐题卡片突出问题正文，元信息层级更轻，选择态清楚但不过度装饰。
- 长文案换行自然，按钮不抢标题视觉，所有状态在桌面与窄屏都保持清晰且不溢出；保留键盘焦点、对比度和可访问标签。
- 开发验收必须在浏览器实际打开完整流程并截图检查；若尺寸、对齐、留白或层级看起来粗糙，继续调整后再交付，不以构建通过作为视觉验收。

## 验收标准

1. 点击“维护品牌知识”能进入编辑；保存后先显示确认信息，取消确认不会产生服务端变更。
2. 确认成功后，展示服务返回的市场列表；市场状态和待处理数量与服务响应一致。
3. 市场候选最多选择 5 条；保存只加入已选候选，原有问题保留，未选候选不加入。
4. 单市场保存成功后回到市场列表且状态更新；开启全部市场后展示服务返回的启用状态。
5. 刷新页面时重新读取 service 状态，组件不从 localStorage 恢复流程状态。
6. 所有读取/提交有明确的 loading、empty、error 和 retry 行为；重复提交被阻止。
7. 通过流程 service 测试、组件/集成测试、`npm test`、`npm run lint`、`npm run build`，并在浏览器中走通完整流程。
8. 浏览器截图对照用户原型验收：弹窗比例紧凑、排版与间距有节奏、状态和操作层级清楚、窄视口不溢出；视觉质量不达标时不得以功能测试通过为由结束。

## 明确不做

- 本期不实现真实后端 API、数据库、鉴权或真实额度扣减；mock 仅供界面联调和验证。
- 不改写市场设置向导、可见性监测其他配置阶段或监测结果分析。
- 不把流程进度、暂停状态或推荐题选择存入 localStorage。
- 不新增截图之外的确认步骤或改变已有监测问题的处理规则。
