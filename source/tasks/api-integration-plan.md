# GEO 后端接口接入计划

## 目标

将前端已有产品页面接到 `geo-agent` 中已实现、且有对应页面消费的业务接口。HTTP 统一复用 `src/api/http.ts` 的委托会话认证和 `WebResult` 约定；响应仅通过显式 adapter 转成 UI 类型。加载失败、空结果和未实现能力要清晰区分，不以静态演示数据冒充线上数据。

## 边界

- 纳入：配置/市场向导、监测执行与指标、报告中心、诊断与策略，以及这些页面已呈现的 API 支持动作。
- 不接入：健康检查、Redis/演示用户测试端点、邮件/LLM 调试端点、由 AI 建站或算法服务调用的入站/出站第三方接口。
- 后端明确标为 TODO 的报告观察处理、报告导出等能力，不在前端伪造成功状态；根据实际实现状态展示不可用/空状态。
- 优化中心任务工作流若无对应后端持久化接口，继续标识为原型/本地演示，不宣称已同步后端。

## 组件与数据边界

- `src/api/*`: 对应后端 Controller 的 typed HTTP 方法，只处理路径、参数和信封错误。
- `src/data/*-api-adapters.ts`: 纯函数，将后端 DTO 映射成页面 view model；空字段保持空，不造默认业务指标。
- Pinia stores / route views: 负责并发加载、加载/错误状态和动作编排；模板只消费 view model。
- 现有页面子组件保持展示职责，通过 props/events 传递数据和操作。

## 实施顺序

1. 建立 API 覆盖清单和契约测试；确认当前报告 API 与会话处理不回归。
2. 市场上下文及配置向导：市场/字典/品牌/人设/问题/平台/主题/候选/向导状态。
3. 监测：计划配置、启停、触发轮次、轮次列表/详情/回答、品牌/平台/人设/信源/问题命中指标、跨轮趋势。
4. 概览、诊断、竞品与信源视图接入相应真实查询；没有服务端接口的工作流明确保留原型边界。
5. 报告中心和详情：补齐后端已实现且页面可用的列表、详情子块、额度、生成任务轮询及导出能力。
6. 汇总 API 覆盖矩阵，移除相关页面中不再使用的模拟数据；全量测试、lint、构建和可运行的联调验证。

## 验收标准

- 每个纳入的页面调用其对应后端 endpoint，契约按 Controller/VO 源码或正式 API 文档定义。
- 同一个页面不会把演示 fixtures 当作请求失败后的静默回退；错误与空数据有独立状态。
- 所有请求继承现有委托 Token；市场切换遵循后端 `/geo/config/market/switch` 上下文规则。
- adapter 对 null、分页结果和字典编码有单元测试；HTTP 参数/路径/错误信封有测试。
- `npm test`、`npm run lint`、`npm run build` 通过；后端联调条件缺失时明确报告，不声称 E2E 通过。

## 风险

- 页面原型字段与后端字段不一致，需要逐项映射；不能根据截图或 fixtures 猜测接口数据。
- 后端当前有 140 个映射，但其中有内部/测试/三方网关用途；产品接入范围按前述边界筛选。
- 部分端点虽有 Controller 但内部仍标 TODO；只纳入确认已实现的逻辑。
- 市场 ID 与 UI 本地市场键、用户上下文中的站点 ID 可能使用不同标识，需以响应 DTO 和会话上下文为准。

## 检查点

- 配置 + 监测查询接入后：相关单测、构建通过，空数据不回退到 fixtures。
- 报告 + 诊断接入后：全量单测、lint、构建通过；真实接口环境可用时再做浏览器联调。
